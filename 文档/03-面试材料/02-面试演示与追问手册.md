## 1. 60 秒项目定位

> 我过去更强的是 C 端增长、会员权益、SKU 和中后台协作，支付方面主要是业务和后端沟通，并没有把自己包装成做过生产级支付网关。看到贵司 JD 同时强调支付流程和开放平台登录认证后，我做了一个入职预演：先写领域对象、三套状态机、异常矩阵、PRD、数据和接口契约，再把它实现成前后端分离的本地系统。重点不是展示我会写多少代码，而是验证我能不能把产品规则落到接口、数据、幂等、补偿和验收，并与研发讨论异常边界。

## 2. 演示前检查

1. 在项目根目录执行 `pnpm dev`。
2. 打开用户端 `http://127.0.0.1:5175`。
3. 打开运营台 `http://127.0.0.1:5174`。
4. 打开 Swagger `http://127.0.0.1:3000/docs` 作为备用。
5. 用户端点“重置演示”，确认订单数为 0。
6. 浏览器缩放保持 100%，关闭与面试无关的标签页。

## 3. 5 至 7 分钟主演示

### 第 1 分钟：展示产品设计底座

打开 `01-产品方案/03-领域对象与关系字典.md` 和 `04-订单支付权益状态机.md`。

话术：

> 我先没有画支付成功页，而是把订单、支付尝试和权益拆成独立对象。订单是购买意图，一笔订单可以有多次支付尝试；支付成功不等于权益到账，所以三套状态必须独立。

只讲一个关键组合：`Order=PAID`、`Payment=SUCCEEDED`、`Entitlement=GRANT_FAILED`。

### 第 2 分钟：正常购买

用户端选择“创作会员月卡” → 选择正常成功 → 创建订单并模拟支付。

话术：

> 创建订单时前端只传用户和 SKU，金额由后端按当前可售 SKU 重算；订单明细固化价格和权益快照。支付尝试单独建模，便于失败后在原业务订单上重试。

结果页指出三列：业务订单、支付状态、权益状态。再指出订单号、支付单号、渠道流水号。

### 第 3 至 4 分钟：主异常与补偿

返回商品中心，购买“AI 创作额度包”，选择“权益发放失败”。

话术：

> 这里故意模拟支付成功但权益服务失败。系统保留资金成功事实，订单停在 PAID，页面明确告诉用户不要重复付款。失败进入异常队列，而不是把支付回滚。

切到运营台 → 异常中心 → 查看链路。

指出：

- Webhook 校验通过后资金事实落库。
- 下一事件才是权益发放失败。
- 关联对象区可以用订单、支付、渠道、权益编号跨系统定位。

点击“确认并补发权益”。

> 人工补发不是直接改数据库状态，而是调用受控业务接口，复用原订单权益快照和幂等键，并记录操作者、原因和前后状态。

### 第 5 分钟：三层幂等

打开 `02-研发对齐与学习/09-支付与认证代码逐层解读.md` 的“三层幂等”。

话术：

> 创建订单用业务幂等键；Webhook 用渠道加事件号去重；权益流水用订单明细加权益定义做幂等。每层都有数据库唯一约束，不能只依赖应用层先查一次。

### 第 6 分钟：开放平台认证

运营台 → 开放平台 → 依次点击授权、换 Token、访问 UserInfo、撤销。

话术：

> 我把第三方登录和开放平台授权分开。前者解决外部身份映射到内部用户，后者解决第三方应用经用户同意后可以访问哪些 Scope。这里实现的是授权码加 PKCE：state 防 CSRF、回调地址精确白名单、授权码一次性且只存哈希、Token 可刷新轮换和撤销。

### 第 7 分钟：收束

> 这不是生产支付系统，真实渠道证书、风控、清结算和容灾仍需结合公司架构设计。但这次预演让我把 PRD 规则逐条对应到了对象、接口、事务和自动化验收。如果入职，我会先基于公司现有支付与开放平台能力做差距分析，而不是推翻重建。

## 4. 高频追问与回答

### 为什么支付成功后不直接把订单改成“完成”？

“已支付”是资金事实，“已完成”表示承诺的权益已经交付。中间有异步履约和失败补偿，所以 `PAID` 与 `FULFILLED` 必须区分。

### 客户端支付成功页能不能作为成功依据？

不能。客户端结果可能被篡改、丢失或早于渠道最终状态。最终以服务端 Webhook 和必要时的主动查单为准。

### 重复回调怎么避免重复发权益？

先以 `provider + providerEventId` 唯一键去重渠道事件，再以权益业务幂等键约束流水。两层分别防重复处理和重复履约。

### 为什么支付和权益不能放在一个大事务？

它们通常跨服务、跨数据库，且支付成功是外部不可逆事实。权益失败不能回滚渠道扣款，所以使用本地事务 + Outbox + 异步补偿实现最终一致。

### 回调金额不一致怎么办？

保存原事件，标记校验拒绝，不更新支付成功，创建高等级异常并主动查单。不能为了“跑通流程”忽略一分钱差异。

### 支付超时但后来收到成功通知怎么办？

关闭订单前先主动查单；迟到成功不能静默丢弃，要根据商品是否仍可履约决定继续履约或自动退款，并完整留痕。

### 幂等键由谁生成？

调用方为一次业务意图生成并在重试时复用；服务端用作用域和幂等键唯一约束。参数变化却复用同一键应返回冲突，不得返回错误资源。

### `state` 和 PKCE 有什么区别？

`state` 绑定授权请求与回调，主要防 CSRF；PKCE 绑定授权码与最初发起授权的客户端，防授权码被截获后换 Token。两者不能互相替代。

### 为什么 Token 只存哈希？

数据库泄露时，明文 Token 可直接调用接口；哈希只能用于校验，不能还原原 Token。明文只在签发时返回一次。

### Scope 怎么设计？

按资源与动作拆最小权限，例如 `orders.read`、`entitlements.read`，请求 Scope 必须同时属于应用允许范围和用户同意范围；API 每次访问还要检查具体 Scope。

### 真实微信支付、支付宝或 Stripe 接入还缺什么？

缺真实渠道 SDK/证书、商户配置、密钥托管和轮换、渠道错误码映射、查单/退款/对账适配、压测、风控、监控告警、容灾和合规评审。Demo 证明的是产品与系统设计能力，不等同生产经验。

### 作为产品经理为什么要看代码？

不是替研发决定实现细节，而是确认关键规则真的落在可执行位置：金额谁计算、状态何时更新、唯一约束在哪、失败如何恢复、验收如何自动化。这样评审更具体，减少需求和实现理解偏差。

## 5. 表达红线

- 不说“我做过生产级支付系统”，说“我完成了教学型入职预演”。
- 不说“这套架构可以直接上线”，主动指出密钥、风控、容灾和合规边界。
- 不把代码量当成果，重点讲产品规则、取舍、异常和验收。
- 不在面试现场展开所有文档，主线只使用状态机、系统页面和代码解读三处。
- 被问到不确定的渠道细节时，先说明需要查官方文档或与渠道技术支持确认，再给出通用系统边界。
