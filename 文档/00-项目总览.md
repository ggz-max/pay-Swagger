# MonetizeLab 项目总览

最后更新：2026-07-31

## 1. 项目目标

在用户产品经理-商业化方向面试前，完成一套可运行、可讲解、可学习的商业化产品闭环，证明候选人能够：

- 系统设计用户、认证、商品、订单、支付、权益、退款、订阅、对账和开放平台。
- 输出研发可执行的 PRD、流程、规则、接口约束和验收标准。
- 理解业务规则如何落到接口、状态机、数据表、异步任务和测试。
- 围绕产品边界、异常处理和验收标准与前端、后端及测试有效沟通。

项目不用于把候选人包装成资深研发或资深支付产品经理，而是作为基于岗位 JD 完成的“入职预演/学习型项目”。

## 2. 候选人定位与边界

- 已有优势：C 端增长、会员权益、SKU、用户分层、付费转化、运营后台、数据平台、H5 原型、数据复盘和跨部门推进。
- 当前短板：没有完整从 0 到 1 负责过支付网关、海外 IAP、Stripe 或 Adyen 接入。
- 面试定位：有商业化前链路和中后台经验，正在系统补齐支付、订单、订阅与开放平台底层机制。
- 表达边界：不得把本项目表述为真实公司生产项目、真实资金系统或既往支付履历。

## 3. 项目方向

- 项目名：MonetizeLab 商业化闭环沙盘。
- 核心场景：C 端 AI 工具的会员、订阅与额度包购买。
- 主链路：登录 -> 商品 -> 订单 -> 支付 -> Webhook -> 权益 -> 退款/补偿 -> 对账/数据。
- 学习投入：支付商业化闭环 70%，登录与开放平台 20%，视觉与看板 10%。
- 实现原则：使用本地支付模拟器，不处理真实资金或真实支付密钥。

## 5. 已确认的产品原则

1. 订单状态、支付状态和权益状态分开建模。
2. 支付最终结果以服务端异步通知和主动查单为准，不能信任客户端单方面返回。
3. 重复 Webhook 必须幂等，不能重复发放权益。
4. 支付成功但权益失败时进入补偿流程，不能要求用户重新付款。
5. 业务订单必须保存商品、价格和权益快照，避免后续商品配置变化污染历史订单。
6. 产品文档必须覆盖正常流程、异常流程、字段规则、错误反馈、数据口径和验收标准。
7. 登录与开放平台设计必须覆盖账号映射、授权范围、回调地址、Token 生命周期和安全边界。
8. 关键业务记录不做物理删除，通过状态、流水和审计记录保留事实。
