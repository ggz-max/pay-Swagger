## 1. 文档说明

### 1.1 文档目标

定义一套面向 C 端 AI 工具的商业化交易与开放平台 MVP，使产品、设计、前端、后端和测试能够基于同一套范围、业务规则和验收标准推进实现。

### 1.2 关联基线

- 《项目背景与用户要求》：解释为什么做。
- 《产品定位与 MVP 范围》：解释做多大。
- 《领域对象与关系字典》：解释业务对象是什么。
- 《订单支付权益状态机》：解释状态如何变化。
- 《异常场景与补偿矩阵》：解释失败后怎么办。

本 PRD 不重复定义对象和状态。出现冲突时，先在上述基线文档中统一，再同步本 PRD。

## 2. 背景与问题

商业化产品不是一个支付按钮，而是一套从购买意图到资金确认、服务履约和售后复盘的业务系统。

本项目需要解决四个核心问题：

1. 用户如何安全登录并选择适合的会员或额度商品？
2. 系统如何确保订单价格可信、支付结果可信且不会重复处理？
3. 支付成功后，如何可靠发放权益并处理部分失败？
4. 运营、客服和财务如何查单、补偿、退款、对账和复盘？

项目同时作为产品经理的技术学习工具，需要通过交易观察台把每次接口调用、状态变化、关键字段和补偿动作解释清楚。

## 3. 产品目标与非目标

### 3.1 产品目标

- 跑通登录、商品、订单、支付、Webhook、权益、退款和异常补偿的完整闭环。
- 正常交易和异常交易均可在前台获得明确反馈，在后台获得可处理入口。
- 所有资金和权益关键动作具备幂等、审计和关联查询能力。
- 用可观察时间线帮助产品经理理解实现机制并与研发评审。
- 形成可以在面试现场 5 至 7 分钟稳定演示的本地产品。

### 3.2 非目标

- 不处理真实资金和真实商户密钥。
- 不实现生产级高并发、跨地域容灾或复杂财务结算。
- 不实现实物库存、物流、优惠券和组合促销。
- 不在 MVP-A 中真实接入微信、支付宝、IAP、Stripe 或 Adyen。
- 不把模拟系统宣传为真实生产支付经验。

## 4. 成功指标

### 4.1 系统正确性指标

| 指标 | 口径 | MVP 目标 |
|---|---|---|
| 重复回调重复履约数 | 重复 Webhook 导致的额外权益次数 | 0 |
| 金额不一致错误履约数 | 金额/币种不符仍发放权益的订单数 | 0 |
| 支付成功可追溯率 | 可关联订单、支付、事件和时间线的成功支付数/成功支付总数 | 100% |
| 补偿可追溯率 | 具有异常工单、重试和解决记录的补偿数/补偿总数 | 100% |
| 人工操作审计率 | 具有操作者、原因和前后状态的高风险操作数/高风险操作总数 | 100% |

### 4.2 业务观察指标

| 指标 | 公式 |
|---|---|
| 下单转化率 | 创建订单用户数 / 商品详情访问用户数 |
| 支付拉起率 | 创建支付尝试订单数 / 有效订单数 |
| 支付成功率 | 存在成功支付尝试的订单数 / 拉起支付订单数 |
| 履约成功率 | `FULFILLED` 订单数 / `PAID` 订单数 |
| 平均权益到账时长 | `fulfilled_at - paid_at` 的平均值及 P95 |
| 退款率 | 成功退款订单数 / 成功支付订单数 |
| 净收入 | 成功支付金额 - 成功退款金额 |
| 异常自动恢复率 | 自动恢复异常数 / 可自动恢复异常总数 |

## 5. 用户角色与权限

| 角色 | 核心目标 | 主要权限 |
|---|---|---|
| C 端用户 | 购买、查看订单与权益、申请退款 | 只能访问本人交易和权益 |
| 运营人员 | 配置商品、查看转化和订单 | 商品管理、只读交易查询 |
| 客服人员 | 诊断到账问题、退款和补偿 | 查单、查事件、提交受控补偿 |
| 财务人员 | 对账、确认差异和退款 | 对账与财务字段，不修改权益 |
| 管理员 | 管理角色、渠道与开放平台应用 | 高风险配置与权限管理 |
| 开放平台开发者 | 创建应用并完成授权接入 | 只能管理自己的应用和凭证 |

高风险操作包括人工补发、权益回收、退款、忽略异常工单、轮换密钥和停用渠道，必须二次确认并填写原因。

## 6. 版本范围

### 6.1 MVP-A：面试主链路，P0

- 本地账号登录和预置演示用户。
- 会员月卡、会员年卡和 AI 额度包。
- 商品列表、商品详情和确认购买。
- 业务订单、模拟支付、异步 Webhook 和主动查单。
- 会员/额度权益发放、查询、失败重试和人工补发。
- 订单列表、订单详情、退款和权益回收。
- 运营后台订单查询、交易时间线和异常中心。
- 重复回调、金额不一致、权益失败和退款回收失败演示。
- 核心业务指标和本地演示数据重置。

### 6.2 MVP-B：主链路稳定后，P1

- 模拟 OAuth/OIDC 授权码登录、PKCE、Token 刷新和撤销。
- 开放平台应用、回调地址和 Scope 管理。
- 自动续费订阅对象和续费周期演示。
- 对账单导入、差异识别和处理。
- 更完整的角色权限和安全告警。

## 8. 核心用户流程

### 8.1 正常购买

```mermaid
flowchart LR
    A["登录"] --> B["选择产品与SKU"]
    B --> C["后端创建订单并保存快照"]
    C --> D["创建支付尝试"]
    D --> E["模拟渠道完成支付"]
    E --> F["Webhook验签、核对、去重"]
    F --> G["订单已支付"]
    G --> H["异步发放权益"]
    H --> I["订单已履约"]
    I --> J["查看权益与交易时间线"]
```

### 8.2 支付成功但权益失败

```text
支付成功 -> 订单 PAID -> 权益 GRANT_FAILED
-> 自动重试 -> 超限创建异常工单 -> 客服人工补发
-> 权益 ACTIVE -> 订单 FULFILLED
```

### 8.3 退款

```text
申请退款 -> 校验可退 -> 渠道退款 -> 资金退款成功
-> 权益回收 -> 订单 REFUNDED
```

资金退款成功但权益回收失败时，订单仍显示已退款，异常中心继续处理权益。

## 9. 功能需求

### 9.1 登录与开放平台

| 需求编号 | 优先级 | 需求描述 | 核心规则/验收 |
|---|---|---|---|
| `FR-AUTH-01` | P0 | 支持预置演示用户一键登录和退出 | 会话只访问本人订单和权益 |
| `FR-AUTH-02` | P1 | 支持模拟第三方授权码登录 | 使用 `state`，授权码一次性且短时有效 |
| `FR-AUTH-03` | P1 | 支持外部身份与内部用户映射 | `provider + provider_subject` 唯一，不自动覆盖冲突绑定 |
| `FR-AUTH-04` | P1 | 支持开放平台应用管理 | `client_id` 唯一，密钥明文只展示一次，回调地址白名单精确匹配 |
| `FR-AUTH-05` | P1 | 支持 Scope 授权、Token 签发、刷新和撤销 | Token 权限不得超过用户授权，撤销后立即失效 |
| `FR-AUTH-06` | P1 | 支持授权与调用审计 | 记录应用、用户、Scope、时间和结果，敏感字段脱敏 |

| 需求编号 | 优先级 | 需求描述 | 核心规则/验收 |
|---|---|---|---|
| `FR-PAY-01` | P0 | 为有效订单创建支付尝试 | 金额来自订单；创建请求幂等 |
| `FR-PAY-02` | P0 | 通过 Provider 接口隔离支付渠道 | 业务层不依赖某个渠道私有字段 |
| `FR-PAY-03` | P0 | 模拟成功、失败、取消、延迟和超时 | 每种结果可重复演示和重置 |
| `FR-PAY-04` | P0 | 接收并保存异步 Webhook | 先保存脱敏原文，再进行业务处理 |
| `FR-PAY-05` | P0 | 校验签名、商户号、金额、币种和订单 | 任一失败不得更新支付成功 |
| `FR-PAY-06` | P0 | 使用渠道事件号去重 | 重放回调不重复状态变化和发权益 |

| `FR-PAY-08` | P0 | 可靠触发支付成功后的权益任务 | 数据库异常后可恢复，事件不会丢 |

## 10. 核心业务规则

| 规则编号 | 规则 |
|---|---|
| `BR-01` | 前端金额不可信，订单金额必须由后端计算。 |
| `BR-02` | 订单明细保存商品、价格、币种和权益快照。 |
| `BR-03` | 一个订单允许多个支付尝试，但最多一个成功结果。 |
| `BR-04` | 客户端返回不能直接产生支付成功。 |
| `BR-05` | Webhook 必须验签、核对金额和去重后才能推进状态。 |
| `BR-06` | 支付成功后 `PaymentAttempt` 永远保留成功事实，退款另建对象。 |
| `BR-07` | 支付成功但权益失败时，订单保持 `PAID` 并进入补偿。 |
| `BR-08` | 同一权益发放幂等键最多成功一次。 |
| `BR-09` | 同一退款幂等键最多向渠道发起一次有效退款。 |
| `BR-10` | 累计成功退款金额不得超过成功支付金额。 |
| `BR-11` | 退款成功与权益回收失败可以同时成立并独立追踪。 |
| `BR-12` | 自动重试超过阈值必须创建异常工单并分配负责人。 |
| `BR-13` | 人工补偿必须走受控业务接口，禁止直接改库。 |
| `BR-14` | 开放平台回调地址精确匹配白名单，Token 权限不超过授权范围。 |
| `BR-15` | 关键业务对象不物理删除，人工操作全部审计。 |

## 11. 数据埋点与指标口径

### 11.1 C 端事件

| 事件名 | 触发时机 | 关键属性 |
|---|---|---|
| `product_viewed` | 打开商品详情 | user_id、product_id、sku_id、source |
| `checkout_started` | 进入确认购买 | sku_id、price、currency |
| `order_created` | 后端创建订单成功 | order_id、order_type、payable_amount |
| `payment_initiated` | 创建支付尝试成功 | order_id、provider、method |
| `payment_result_viewed` | 查看支付结果页 | order_status、payment_status、entitlement_status |
| `entitlement_available` | 权益可用 | entitlement_code、latency_ms |
| `refund_requested` | 提交退款申请 | order_id、reason_code |

### 11.2 服务端事实事件

| 事件名 | 事实来源 |
|---|---|
| `payment.succeeded` | 可信 Webhook 或主动查单 |
| `payment.failed` | 渠道权威失败结果 |
| `entitlement.granted` | 权益事务成功 |
| `entitlement.grant_failed` | 权益发放失败 |
| `refund.succeeded` | 渠道退款权威结果 |
| `entitlement.revoked` | 权益回收事务成功 |
| `exception.created/resolved` | 异常中心状态变化 |

收入和支付成功率必须使用服务端事实事件，不使用前端页面埋点判断资金结果。

## 12. 非功能需求

### 12.1 一致性与幂等

- 创建订单、创建支付、Webhook、权益发放、退款和权益回收均有稳定幂等键。
- 状态更新和待处理事件写入不得出现“状态已改、事件丢失”。
- 关键唯一约束由数据库保证，不能只依赖前端或内存判断。

### 12.2 性能建议基线

- 本地演示环境下，商品、订单和权益查询 P95 小于 500ms。
- Webhook 在完成持久化后尽快返回渠道确认；耗时履约异步执行。
- 订单详情在 2 秒内展示聚合结果和首屏时间线。

### 12.3 安全与隐私

- 密钥和 Token 不以明文持久化或出现在日志/观察台。
- 手机号、邮箱、原始支付载荷按角色脱敏。
- 后台高风险操作需要权限、二次确认和原因。
- Webhook 验签使用原始请求体，防止解析后内容变化影响校验。
- OAuth 使用 `state`；模拟授权码一次性、短时有效；PKCE 在 MVP-B 实现。

### 12.4 可观测与恢复

- 核心动作具有 `correlation_id`、标准事件名和结构化错误码。
- 重试任务具有次数、下次执行时间、最后错误和人工接管状态。
- 本地演示支持确定性种子数据和一键重置。

### 12.5 可用性与无障碍

- 用户状态文案不暴露内部枚举和技术错误。
- 支付处理中、到账延迟和退款处理中均有清晰下一步。
- 主要页面支持键盘操作、可见焦点和合理颜色对比。

## 13. 验收标准

### 13.1 正常主链路

| 验收编号 | 操作 | 预期结果 |
|---|---|---|
| `AC-01` | 登录并购买会员月卡 | 创建订单、支付尝试、成功事件、权益和权益流水 |
| `AC-02` | 购买年卡时已有有效会员 | 到期时间按叠加规则延长 |
| `AC-03` | 购买额度包 | 余额正确增加并记录前后值 |
| `AC-04` | 支付失败后更换方式重试 | 同一订单保留两次支付尝试，只第二次成功 |
| `AC-05` | 支付完成后关闭页面再进入 | 订单详情显示最终支付和权益结果 |
| `AC-06` | 对成功订单发起全额退款 | 退款成功、权益回收、订单显示已退款 |

### 13.2 异常主链路

必须通过异常矩阵中的 `AT-EX-01` 至 `AT-EX-10`。

### 13.3 登录与开放平台

| 验收编号 | 操作 | 预期结果 |
|---|---|---|
| `AC-AUTH-01` | 正常授权码登录 | 创建或匹配用户身份并建立会话 |
| `AC-AUTH-02` | 修改 state 或重复使用授权码 | 请求被拒绝且不创建会话 |
| `AC-AUTH-03` | 使用越权 Scope 调用 API | 返回标准禁止访问错误并记录审计 |
| `AC-AUTH-04` | 撤销授权后使用旧 Token | Token 立即失效 |

### 13.4 后台与观察台

| 验收编号 | 操作 | 预期结果 |
|---|---|---|
| `AC-ADM-01` | 使用任一核心编号搜索 | 定位到同一交易详情 |
| `AC-ADM-02` | 查看支付成功订单时间线 | 显示接口、事件、状态变化和脱敏载荷 |
| `AC-ADM-03` | 执行人工补发 | 二次确认、原因必填、幂等且有审计 |
| `AC-ADM-04` | 筛选 S1/S2 未解决异常 | 结果、负责人、重试和 SLA 信息准确 |

## 14. 发布与演示准备

### 14.1 发布前检查

- P0 需求全部通过自动化或人工验收。
- 种子数据包含正常、失败、迟到、重复和补偿场景。
- README 包含一条命令启动和一条命令重置。
- 演示环境不包含真实密钥、真实手机号或真实支付数据。
- 页面无明显溢出、重叠、空白画布或控制台错误。
- 关键演示流程具备截图或录屏备用材料。

### 14.2 演示主线

1. 第三方/演示用户登录。
2. 选择年卡并创建订单。
3. 模拟支付成功并查看 Webhook 时间线。
4. 重放回调证明权益不重复。
5. 模拟权益失败并执行补偿。
6. 发起退款，观察资金和权益分别变化。
7. 打开指标与异常中心说明上线后如何运营。

## 15. 风险与取舍

| 风险 | 取舍 |
|---|---|
| 面试前时间有限 | 先实现 MVP-A 的支付与权益主链路，开放平台和订阅作为 P1 |
| 真实支付接入需要资质 | 使用行为逼真的本地 Provider，明确模拟边界 |
| 后台范围容易膨胀 | 只保留查单、观察、补偿、退款和异常处理能力 |
| 文档和代码可能不一致 | 使用需求编号和追踪矩阵，变更时同步更新 |
| 候选人陷入代码语法 | 学习顺序坚持 PRD -> 状态 -> 接口 -> 数据 -> 代码 -> 测试 |

## 16. 研发评审必须回答的问题

1. 哪些写操作处于同一数据库事务？
2. 支付成功事件如何保证不丢且只履约一次？
3. 主动查单和 Webhook 同时到达时如何避免竞争？
4. 前端如何组合订单、支付、权益和退款状态？
5. 权益发放和回收如何通过唯一约束保证幂等？
6. 异常工单由哪些规则创建、升级和关闭？
7. 观察台怎样脱敏但仍保留排障价值？
8. OAuth 密钥、授权码和 Token 如何存储与撤销？
9. 哪些验收用例必须自动化，哪些可以人工验证？
10. 如何用种子数据稳定复现每个演示场景？

## 17. Definition of Done

一个需求只有同时满足以下条件才算完成：

- PRD 规则明确且没有未解决的关键歧义。
- 页面和接口具备正常、空、加载、失败和权限不足状态。
- 数据模型与状态机一致。
- 关键写操作具备幂等、审计和错误码。
- P0 正常与异常验收通过。
- 交易观察台能够解释该需求产生的核心事件。
- 对应代码学习地图已经说明“业务规则 -> 接口 -> 数据 -> 代码 -> 测试”。
