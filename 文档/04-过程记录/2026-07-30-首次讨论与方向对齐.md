# 2026-07-30 首次讨论与方向对齐

> 历史说明：本文保留首次讨论时的目录名称。当前目录结构以 `../00-项目总览.md` 为准。

## 1. 用户初始诉求

用户准备参加北京沃客来福科技“用户产品经理-商业化方向”的第一次线下面试，希望通过一个完整的小项目提前模拟入职后的产品工作。

用户指出两个重点缺口：

- 支付经验此前主要停留在与后端沟通、表面知识和业务知识理解。
- JD 特别提到开放平台对接和登录认证，需要补齐系统理解。

用户希望项目同时包含产品经理文档、研发对齐材料、前后端分离代码和可运行闭环，并在代码完成后从产品经理角度学习底层框架与关键接口。

## 2. 第一轮建议摘要

建议将项目定义为“商业化交易与开放平台沙盘”，而不是只做一个支付页面。

完整业务闭环为：

```text
用户登录 -> 商品与订阅 -> 创建订单 -> 支付 -> 异步回调
-> 权益发放 -> 退款/补单/对账 -> 数据复盘
```

第一轮明确了以下建议：

- 使用模拟支付 Provider，避免真实商户资质、密钥和网络依赖。
- 前后端分离，同时提供 C 端用户产品和运营管理后台。
- 现场演示突出重复回调、权益失败、退款和对账，而不是堆积页面。
- 项目应诚实定位为“基于 JD 的入职预演”，不能冒充既往生产经验。
- 面试演示控制在 5 到 7 分钟。

## 3. 第二轮需求深化

用户进一步明确：岗位核心仍是产品经理，真正目标是学会如何设计系统、写好 PRD，并能和研发无障碍沟通。

因此项目目标调整为：

> 可执行 PRD + 可观察业务系统 + 产品经理技术学习手册。

代码不再只是演示产物，而是用来解释：

- 业务规则如何落到接口。
- 状态如何存入数据库。
- 异步通知如何触发后续处理。
- 支付成功和权益到账为什么不是同一件事。
- 幂等、重试和补偿解决什么业务风险。

## 4. 第二轮建议摘要

学习重点占比确定为：

- 支付商业化闭环 70%。
- 登录认证与开放平台 20%。
- 页面视觉和数据看板 10%。

新增“交易链路观察台”作为项目核心能力。每笔交易应展示事件时间线、接口请求、状态变化、数据写入、幂等键和失败后的处理策略。

同时明确三套状态必须分开设计：

- 订单状态。
- 支付状态。
- 权益状态。

产品经理的学习顺序确定为：业务场景 -> 核心对象 -> 状态机 -> 异常 -> 接口 -> 数据 -> 异步与补偿 -> 代码与测试。
