# 测试策略与需求追踪矩阵

版本：V1.0  
状态：阶段 2 研发契约  
最后更新：2026-07-30

## 1. 文档目的

确保每条产品需求、业务规则、状态转换和高风险异常都有可执行的验证证据，避免“页面能点”被误认为“系统闭环正确”。

本文件在代码阶段作为测试清单和完成门禁。测试文件名、用例标题和缺陷记录应保留这里定义的测试 ID。

## 2. 测试层次

| 层次 | 验证重点 | 运行方式 | 适合场景 |
|---|---|---|---|
| 领域单元测试 | 金额、状态转换、叠加规则、错误分类 | 无网络、快速运行 | 每次保存和提交 |
| 服务集成测试 | 事务、唯一约束、Outbox、并发和补偿 | 临时 SQLite 数据库 | 后端改动后 |
| API 契约测试 | 认证、请求响应、错误码和幂等头 | 启动 API 进程 | 接口完成后 |
| 端到端测试 | 用户/后台完整流程和可见状态 | Playwright 本地浏览器 | P0 流程和发布前 |
| 安全测试 | 验签、授权、Scope、重放和脱敏 | API/集成测试 | 认证和支付变更后 |
| 人工探索测试 | 易用性、文案、异常恢复和演示节奏 | 本地桌面/移动视口 | 版本冻结前 |

## 3. 测试环境与确定性

- 测试数据库每次独立创建，测试结束后销毁。
- 固定系统时间或注入 Clock，稳定测试订单过期、Token 到期和订阅周期。
- ID 和业务编号生成器可在测试环境注入确定性序列。
- 支付模拟器可选择成功、失败、取消、延迟、超时、重复、乱序和篡改载荷。
- 后台任务支持单步执行，不依赖真实等待 15 分钟。
- 每个测试自行创建数据，不依赖测试执行顺序。
- 测试不调用真实外部支付、短信、邮件或 OAuth 服务。

## 4. 当前测试命令与结果

```text
pnpm typecheck            全工作区严格TypeScript检查
pnpm test                 共享领域规则单元测试
pnpm build                API与两个前端生产构建
pnpm test:e2e             Playwright桌面/移动业务和视觉测试
pnpm verify               类型检查、单测和生产构建
```

2026-07-30 实际结果：领域规则 2/2 通过；类型检查和生产构建全部通过；Playwright 10/10 通过。数据库事务、API 契约、Webhook 去重、异常补偿和 OAuth 安全目前由端到端测试与专项 HTTP 验证覆盖，尚未拆成独立 `test:integration`、`test:api`、`test:security` 命令。

Playwright 使用 1 个 worker，原因是桌面与移动项目共享本地演示数据库，每条用例会重置交易数据；串行执行避免并行重置造成非确定性。生产级测试应为每个 worker 分配独立数据库。

## 10. Playwright 端到端场景

### 10.1 桌面视口

- 路由：C 端购买 `/store`，订单详情 `/orders/{id}`，后台 `/admin`。
- 视口：`1440x900`。
- 检查：主链路、异常补偿、退款、时间线、无控制台错误、无失败网络请求。

### 10.2 移动视口

- 路由：登录、商品、支付结果、订单详情和权益中心。
- 视口：`390x844`。
- 检查：文本不溢出、按钮可点击、状态不重叠、支付结果和客服入口可见。

### 10.3 必备 E2E

1. 月卡正常购买到账。
2. 支付失败后在同一订单重试成功。
3. 支付成功后关闭页面再进入。
4. 重复 Webhook 不重复权益。
5. 权益失败自动重试和人工补发。
6. 全额退款和权益回收。
7. 退款成功但权益回收失败。
8. 多编号搜索和交易观察台。

## 11. 安全测试

- Webhook：错误签名、旧时间戳、缺失事件号、篡改金额、超大请求体。
- OAuth：state 不匹配、PKCE 失败、授权码重用、回调地址差异、Scope 越权。
- 资源权限：用户 A 访问用户 B 的订单、权益和退款。
- 后台权限：运营尝试人工补发、客服尝试对账关闭、普通用户访问后台。
- 脱敏：日志、时间线、错误响应和截图中搜索密钥、Token、手机号和邮箱明文。

## 13. 缺陷分级

| 等级 | 标准 | 示例 |
|---|---|---|
| Blocker | 资金/权益错误、安全绕过、数据不可恢复 | 重复扣款、重复权益、越权查单 |
| Critical | P0 主链路不可完成或补偿不可用 | Webhook 无法处理、人工补发失败 |
| Major | 功能可完成但状态、指标或错误反馈明显错误 | 退款显示失败但实际成功 |
| Minor | 不影响主流程的视觉或低频问题 | 非关键文案、间距不一致 |

## 15. 产品经理需要掌握的沟通点

1. 测试不是“按页面点一遍”，而是验证业务不变量和状态边界。
2. 单元测试证明规则，集成测试证明事务和约束，E2E 证明用户闭环。
3. 幂等和并发必须通过重复/并发调用验证，不能只检查代码存在。
4. 失败注入用于证明系统真的能补偿，而不是文档声称可以。
5. 每条需求需要可定位的测试 ID，才能判断版本是否真正完成。
