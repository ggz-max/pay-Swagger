# 产品经理技术学习框架

## 1. 学习目标

学习代码的目标不是独立完成生产级支付系统，而是能够：

- 看懂一条业务规则经过哪些系统环节。
- 判断研发方案是否覆盖正常状态和异常状态。
- 与前端讨论交互、接口调用和最终状态展示。
- 与后端讨论对象模型、接口、状态转换、幂等、事务、重试和补偿。
- 与测试讨论可验证的验收条件和边界用例。

## 2. 正确学习顺序

1. 业务目标和用户场景。
2. 核心对象以及对象之间的关系。
3. 状态机和状态转换条件。
4. 正常流程与异常流程。
5. 接口输入、输出、错误码和调用方。
6. 数据为什么这样保存。
7. 异步回调、幂等、事务、重试和补偿。
8. 对照代码验证实现。

不从 TypeScript 语法开始，也不要求记忆框架装饰器。先理解业务事实，再理解代码如何承载事实。

## 3. 每个功能的三层映射

| 产品层 | 研发实现层 | 学习与沟通重点 |
|---|---|---|
| 用户点击购买 | `POST /orders` | SKU、价格快照、订单有效期、重复下单 |
| 拉起支付 | `POST /payments` | 订单与支付单关系、支付方式、重试 |
| 支付完成 | Webhook | 验签、金额核对、去重、可信结果来源 |
| 发放会员 | 事件或任务 | 幂等、有效期、失败重试、人工补发 |
| 查询结果 | `GET /orders/{id}` | 轮询、最终一致性、用户提示 |
| 申请退款 | `POST /refunds` | 可退金额、退款审核、权益回收 |
| 第三方登录 | OAuth 回调 | state、授权码、账号映射、绑定解绑 |
| 开放平台授权 | Token 与 Scope | 权限、过期、刷新、撤销、回调安全 |

## 4. 代码学习地图模板

后续每条重要规则都按以下格式记录：

```text
业务问题：为什么需要这条规则？
PRD规则：用户和系统应该表现成什么样？
接口：哪个请求或事件触发？
数据：保存了哪些事实和状态？
代码：规则在哪个模块实现？
测试：怎样证明实现符合规则？
异常：失败后谁处理，用户看到什么？
面试表达：如何在30秒内说明？
```

示例：

```text
业务问题：支付渠道可能重复发送成功通知。
PRD规则：重复通知不能造成重复发放权益。
接口：POST /webhooks/payments/mock。
数据：provider_event_id 建立唯一约束。
代码：支付回调服务先执行事件去重，再更新支付状态。
测试：连续发送三次相同事件，只生成一条权益记录。
异常：重复事件记录为 ignored，不作为系统错误展示给用户。
面试表达：通过渠道事件唯一键和权益发放幂等键做双重保护。
```

## 5. 学习完成标准

对每个核心模块，候选人应能回答：

1. 为什么存在这个模块？
2. 它接收什么输入，产生什么输出？
3. 保存了哪些关键数据？
4. 有哪些状态，谁有权改变状态？
5. 最危险的三个异常是什么？
6. 如何重试，如何防止重复处理？
7. 用户看见什么，后台人员如何处理？
8. 产品如何验收，数据如何复盘？
